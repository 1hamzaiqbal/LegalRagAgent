# Bottleneck-Aware Diagnostic Adaptation Framework

Date: 2026-05-10

## Goal

Develop and evaluate a bottleneck-aware diagnostic adaptation framework for
legal RAG, where calibration traces determine when and how to apply Snap-HyRE /
HyRE, metadata filtering, option grounding, query rewriting, or verifier
policies across legal benchmarks.

This preserves Snap-HyRE as a central intervention family, but makes the paper
about diagnosing when generated reasoning helps instead of adding one fixed
Snap-HyRE prompt everywhere.

## Direction

The main direction is bottleneck-aware adaptation. A narrower "Snap-HyRE as an
add-on" story remains useful for class-report and workshop framing, but it
risks collapsing into prompt engineering unless the lifts are consistently
strong. The more research-shaped claim is that legal RAG benchmarks expose
different failure modes, and calibration traces can route each task to the
intervention it actually needs.

## Evidence Behind The Pivot

The current N=200 legal evidence does not support a single universal Snap-HyRE
prompt. It supports bottleneck-aware routing:

| Dataset | Diagnostic signal | Best current route | Interpretation |
|---|---|---|---|
| BarExam | Snap-HyRE increases accuracy from 80.0% to 86.0% while gold retrieval remains rare | `adaptive_snap_hyre_v2` | Generated reasoning helps answer-option legal reasoning more than literal passage recall. |
| HousingQA | Gold retrieval changes modestly, but verifier accuracy reaches 74.5% | `adaptive_snap_hyre_housing_verifier` | Main bottleneck is conservative statutory entailment, especially false-positive Yes behavior. |
| CaseHOLD | Gold retrieval improves slightly, but accuracy stays flat or drops across several selectors | `adaptive_snap_hyre_diverse` / unresolved | Retrieval exposure is not enough; answer-option conversion is the hard bottleneck. |
| LegalBench-SCALR | Snap-HyDE/frontier sharply improves retrieval exposure and modestly improves accuracy | `adaptive_snap_hyre_frontier` plus disagreement replay | Retrieval/query formulation helps, with additional headroom in disagreement rows. |

Primary diagnostic table: `docs/legal_rag_diagnostic_table_2026-05-10.md`.

## Diagnostic Packet

For each dataset/method calibration slice, compute:

- accuracy;
- recall@1/5/10 and MRR where `gold_idx` / `retrieved_ids` support rank;
- gold retrieved but wrong;
- gold missing but correct;
- accuracy conditional on gold retrieved;
- accuracy conditional on gold missing;
- average LLM calls;
- parse/API/retrieval health.

These are generated by:

```bash
python scripts/build_rag_diagnostic_table.py ...
```

## Bottleneck Labels

The controller should assign one primary bottleneck and optional secondary
flags:

| Bottleneck label | Trigger pattern | Route |
|---|---|---|
| `query_retrieval_gap` | low gold retrieval and low accuracy when gold is missing | `snap_hyre`, `diverse_hyre`, or `query_rewrite_rag` |
| `answer_conversion_gap` | gold retrieved but wrong remains high | `option_grounded_hyre`, `candidate_verifier`, or calibrated selector |
| `statutory_entailment_gap` | yes/no task with unsupported affirmative errors | `state_filter_verifier` |
| `metadata_scope_gap` | task has jurisdiction/state metadata and generic retrieval underperforms filtered retrieval | `state_filter` plus verifier |
| `method_disagreement_gap` | methods disagree and oracle headroom is high | `disagreement_arbitrator` or `reject_or_escalate` |
| `stable_easy_case` | methods agree with high conditional accuracy | cheapest passing route |

## Rule-Based Controller Draft

Initial controller policy:

1. If dataset/task is Housing-style yes/no statutory QA, use
   `state_filter_verifier`.
2. If answer choices are legal holdings and gold retrieval is high but
   gold-retrieved-wrong is nontrivial, use `option_grounded_hyre`; for CaseHOLD,
   keep unresolved rows eligible for `reject_or_escalate`.
3. If Snap-HyRE increases retrieval exposure and accuracy over plain RAG, use
   `snap_hyre` or the audited frontier route.
4. If methods disagree and historical disagreement oracle is high, run a
   cached disagreement arbitrator; otherwise keep the strongest source method.
5. If none of the diagnostics indicate lift, keep `plain_rag` or
   `query_rewrite_rag` as the low-cost route.

## Next Evaluation

Immediate next experiment should be controller-shaped, not another broad prompt
sweep:

1. Build a calibration packet from the existing N=200 logs.
2. Use the above rules to select one route per dataset:
   - BarExam: `adaptive_snap_hyre_v2`.
   - HousingQA: `adaptive_snap_hyre_housing_verifier`.
   - CaseHOLD: `adaptive_snap_hyre_diverse`, with explicit unresolved
     answer-conversion diagnosis.
   - LegalBench-SCALR: `adaptive_snap_hyre_frontier` plus disagreement replay.
3. Evaluate the routed portfolio on a fresh held-out slice if available. If not,
   run a clean N=200 replay/control comparison and mark it as calibration-slice
   evidence.
4. Treat non-HyRE legal query rewrite as both a control and a possible route.
   This separates "generated reasoning helps" from "better legal search
   formulation helps," and gives the controller a cheaper policy when
   hypothetical reasoning is unnecessary.

## Paper Claim

Do not claim that Snap-HyRE solves legal RAG. Claim that generated reasoning is
useful when routed to the right bottleneck, and that legal RAG needs auditable
diagnostics because different benchmarks fail for different reasons.

Current defensible phrasing:

> Snap-HyRE-style methods improve or match strong baselines on most legal tasks,
> but their value depends on the active bottleneck. A diagnostic adaptation
> framework makes these choices explicit and auditable.
